## Deep Digests

### ShinyHunters uses WAF bypass trick in Oracle PeopleSoft attacks
**Problem:** Orgs mitigated a PeopleSoft RCE (CVE-2026-35273) by blocking `/PSEMHUB/` at the WAF instead of patching.
**Approach:** Attackers request `/%50SEMHUB/` — an encoded P. The WAF matches the undecoded path and passes it; WebLogic decodes it and routes to the real endpoint anyway. Serialized Java objects sent there trigger RCE, then web shells and a backdoor give persistence.
**Result:** ShinyHunters compromised dozens of protected servers across education, healthcare, and government for extortion.
**Why it matters:** A WAF rule matched on a literal path does not fix the app — any decode mismatch reopens the hole.
**Jargon:** WAF — filters HTTP requests. URL-encoding — chars as percent-codes. RCE — remote code execution. Web shell — backdoor script run via HTTP.
(link: https://www.bleepingcomputer.com/news/security/shinyhunters-uses-waf-bypass-trick-in-oracle-peoplesoft-attacks/)

### Abusing SQL to Play DOOM
**Problem:** Can a real-time game engine run entirely as database queries, with no application code driving the logic?
**Approach:** CedarDB engineers stored DOOM assets (textures, sprites, maps) as tables, then wrote ~1,300 lines of SQL across 89 chained common table expressions to render each frame, plus ~4,000 lines for game state. A thin Python shim reads the keyboard and shows the bitmap at 35 fps.
**Result:** A playable port of 1993 DOOM whose renderer and game loop are pure SQL.
**Why it matters:** It shows SQL set-based queries can do real-time, stateful computation, not just data retrieval.
**Jargon:** WAD — DOOM asset files. CTE — a named result set inside a query. Bitmap — a pixel array for one frame.
(link: https://hackaday.com/2026/09/25/abusing-sql-to-play-doom/)
