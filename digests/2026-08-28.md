## Deep Digest 1: JavaScript Obfuscation, From Party Trick to Phishing Kit

**Problem:** Obfuscated JavaScript is now routine in phishing kits, malware loaders, and even npm packages, hiding malicious intent from both human review and simple text-based scanners.

**Approach, in plain words:** Talos catalogs the tricks: static ones like hex/Base64 string encoding, junk identifier names, and lookup tables; and runtime ones like `eval`-based code generation, control-flow flattening (turning straight-line logic into a tangled state machine), anti-debugging checks, and JSFuck (valid JS written using only six punctuation characters). Their recommended defense is dynamic: beautify the code, then actually run it in a sandbox and watch what it does rather than trying to manually decode it.

**Result:** A practical triage workflow — preserve the original, beautify, extract strings, find where decoded code executes, and capture the real payload at runtime.

**Why it matters:** The same tricks hitting browsers now hit build pipelines and CI, where hidden code can reach SSH keys and npm tokens — runtime observation catches what static grep misses.

**Jargon:** *Obfuscation* — deliberately scrambling code to hide what it does while keeping it working. *Control-flow flattening* — restructuring a program's logic into a single loop/switch so its execution order isn't visible from the code shape. *Sandbox* — an isolated environment for safely running untrusted code. *BYOVD* — "bring your own vulnerable driver," abusing a legitimately signed driver to gain kernel-level access.

## Deep Digest 2: Saving 100 Terabytes of Memory on 1.1.1.1's DNS Cache

**Problem:** Cloudflare's 1.1.1.1 resolver caches billions of DNS records fleet-wide, and the cache's own bookkeeping overhead was ballooning far past the actual answer data being stored.

**Approach, in plain words:** Engineers rebuilt the cache's internal data structures — replacing generic, pointer-heavy containers with compact, purpose-built layouts that pack DNS records more tightly in memory, and tuned how entries are indexed and expired to cut per-record overhead.

**Result:** Roughly 100 terabytes of memory reclaimed across the resolver fleet, letting existing hardware hold far more cached records without adding servers.

**Why it matters:** A bigger, denser cache means more DNS answers get served instantly instead of triggering a fresh lookup, directly cutting latency for a service handling trillions of queries.

**Jargon:** *DNS cache* — a resolver's local memory of previous domain-to-IP lookups, avoiding repeat queries upstream. *Memory overhead* — extra memory a data structure uses beyond the actual data it stores. *Resolver* — the server that looks up a domain name's IP address on a client's behalf. *Data structure* — the specific in-memory layout used to organize and access data efficiently.
